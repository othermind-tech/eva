# EVA Build System

This directory contains the Electron main process, NSIS installer customisation, packaging configuration, and all build scripts that produce the `EVA-Setup.exe` installer.

---

## Directory Structure

```
build/
  main.js                   Electron main process — static file server + API proxy + backend spawner
  preload.js                Electron context bridge — IPC surface exposed to the renderer
  cdpRelay.js               Chrome DevTools Protocol relay for the embedded preview pane
  ws-vendor/                Vendored `ws` WebSocket library used by cdpRelay.js
  splash.html               Startup splash screen (440×320px frameless window)
  splash-preload.js         Preload for the splash window
  custom.nsh                NSIS customisation — branding + uninstall data-deletion dialog
  after-pack.js             Electron Fuses hook — bakes security flags into EVA.exe after packaging
  obfuscate-renderer.js     Optional JS bundle obfuscation (off by default; build-electron.ps1 -Obfuscate)
  sign.js                   Code signing hook stub (no-op until a signing certificate is configured)
  package.json              electron-builder config + npm scripts
  package-lock.json         Dependency lockfile
  assets/
    icon.ico / icon.png     App, installer and uninstaller icon (generated by scripts/make_icons.py)
    tray-white*.png         Tray icon for dark taskbars  (16 px + @1.25x / @1.5x / @2x)
    tray-black*.png         Tray icon for light taskbars (same sizes)
  scripts/
    build-all.ps1           Convenience wrapper — runs all three build scripts in sequence
    build-backend.ps1       Step 1 — PyInstaller: bundles Python backend into a self-contained .exe
    build-frontend.ps1      Step 2 — Vite: produces frontend/dist/ production bundle
    build-electron.ps1      Step 3 — electron-builder: produces installer/EVA-Setup.exe
```

Output (gitignored, created by the build scripts):
```
installer/
  EVA-Setup.exe             Final deliverable, published as a GitHub Release asset on every tag
  win-unpacked/             Unpacked app (intermediate; not shipped directly)
```

## Runtime Files

### `main.js` — Electron Main Process

Owns the full application lifecycle: starts the splash window, serves the React SPA, spawns the Python backend, waits for it to be healthy, then shows the main window.

**Static file server** — Node.js `http.createServer` on `http://127.0.0.1:5174`. Serves `resources/frontend_dist/` (React SPA). All non-file paths fall back to `index.html` (SPA routing).

**API proxy** — Routes `/api/*` → `http://127.0.0.1:8000`, stripping the `/api` prefix. Matches the Vite dev server proxy exactly so frontend code is identical in dev and production.

Critical proxy implementation details:

| Detail | Why it matters |
|---|---|
| Hop-by-hop header stripping | Node.js decodes `Transfer-Encoding: chunked` automatically. Forwarding that header while piping decoded data causes the browser to mis-parse SSE streams. Headers stripped: `transfer-encoding`, `connection`, `keep-alive`, `te`, `trailers`, `upgrade`, `proxy-authenticate`, `proxy-authorization`. |
| `res.flushHeaders()` | Called immediately after `res.writeHead()`. Without this, `fetch()` does not resolve until the first data chunk arrives, which breaks SSE connection establishment. |
| `socket.setNoDelay(true)` on both sockets | SSE sends tiny chunks (~25 bytes). Nagle's algorithm holds these waiting for a TCP ACK. Chromium uses delayed-ACK (200–500ms), creating a stall that triggers the 60s WorkerDown timeout. Applied to both the browser→proxy socket and the proxy→backend socket. |
| `socket.setTimeout(0)` on both sockets | Prevents Node.js from closing long-lived SSE connections due to inactivity. |

**Port overrides** — Set `EVA_BACKEND_PORT` / `EVA_FRONTEND_PORT` before launching to use ports other than 8000 / 5174.

**Backend spawner** — Launches `resources/backend/eva-backend.exe` as a child process. Injects all required environment variables:

| Variable | Value | Purpose |
|---|---|---|
| `EVA_CONFIG_DIR` | `%APPDATA%\EVA` | Root for all user data |
| `DATABASE_URL` | `sqlite+aiosqlite:///%APPDATA%/EVA/eva.db` | SQLite in AppData — survives reinstalls |
| `CORS_ORIGINS` | `http://127.0.0.1:5174` | Allows frontend origin for CORS preflight |
| `EVA_LOG_DIR` | `%APPDATA%\EVA\logs\` | Backend log output location |
| `TIKTOKEN_CACHE_DIR` | `_internal/tiktoken_cache/` | Points to bundled BPE encoding files |
| `PYTHONUNBUFFERED` | `1` | Forces stdout/stderr to flush immediately |
| `PYTHONDONTWRITEBYTECODE` | `1` | Suppresses `.pyc` file creation inside the bundle |
| `HF_HUB_OFFLINE`, `TRANSFORMERS_OFFLINE` | `0` | Leave HuggingFace downloads allowed (legacy setting; the ONNX embedding model is bundled) |
| `PATH` | Prepended with `_internal/` (and `_internal/torch/lib`, `_internal/torch/bin` if they exist) | Resolves bundled DLLs on Windows. PyTorch is no longer bundled, so the torch entries are normally skipped. |

`main.js` does not set `CHROMA_PATH` or `EVA_WORKSPACE_ROOT`; the backend defaults apply (the vector store and workspace live under `~/eva_workspace`, outside `%APPDATA%\EVA`).

**Health polling** — Polls `GET http://127.0.0.1:8000/health` every 1 second, up to 180 seconds. If the backend does not respond in time, shows an error dialog and quits. First launch takes ~60s (model loading); subsequent launches ~5–10s.

**Graceful shutdown** — `before-quit` runs `stopBackend()`. It first POSTs to the backend's `/internal/shutdown` (3 s timeout) so the backend can sweep its background processes and exit cleanly. If that fails, or the backend is still running after 6 seconds, it falls back to SIGTERM and then SIGKILL. `win-close` goes through `handleCloseAttempt()`, which confirms with the user before quitting if work is in progress.

**IPC handlers:** `open-path`, `get-version`, `win-minimize`, `win-maximize`, `win-close`, `install-update`, `preview-open`, `preview-close`, `preview-set-bounds`, `preview-navigate`, `read-image-file`. The main process also sends `win-maximize-state`, `update-status`, `app-updated`, `app-installed` and `preview-url-changed` to the renderer.

### `preload.js` — Context Bridge

Exposes `window.electronAPI` to the renderer. The renderer never accesses Node.js directly (`contextIsolation: true`, `nodeIntegration: false`).

Exposed: `openPath`, `getVersion`, `platform`, `minimizeWindow`, `maximizeWindow`, `closeWindow`, `onMaximizeChange`, `offMaximizeChange`, `onUpdateStatus`, `offUpdateStatus`, `installUpdate`, `onAppUpdated`, `offAppUpdated`, `onAppInstalled`, `offAppInstalled`, `previewOpen`, `previewClose`, `previewSetBounds`, `previewNavigate`, `onPreviewUrlChanged`, `offPreviewUrlChanged`, `readImageFile`

## Packaging Files

### `package.json` — electron-builder Configuration

```json
"extraResources": [
  { "from": "../backend/backend-dist/eva-backend/", "to": "backend/" },
  { "from": "../frontend/dist/",                   "to": "frontend_dist/" }
]
```

`extraResources` is how the Python backend binary and React bundle get included in the installer. electron-builder copies them into `resources/` at package time, accessible at runtime via `process.resourcesPath`.

Output directory is `../installer` (sibling of `build/`, not inside it). This avoids a Windows case-insensitive filesystem collision where electron-builder would try to package its own output directory when both `build/` (source) and `Build/` (output) resolve to the same path.

NSIS settings: `oneClick: false` (shows installer wizard), `allowToChangeInstallationDirectory: true`, `include: "custom.nsh"` (injects NSIS customisations).

> **Artifact naming rule:** Never use spaces in `artifactName`. GitHub converts spaces to dots in release asset download URLs (`EVA Setup.exe` → served as `EVA.Setup.exe`), but electron-builder writes the space-literal filename into `latest.yml`. electron-updater then percent-encodes the space (`EVA%20Setup.exe`) and gets a 404, silently stalling the download. Use hyphens: `EVA-Setup.exe`.

### `custom.nsh` — NSIS Installer Customisation

**`customInstall`** — Runs in the installer's main Section on every install (fresh, reinstall, and silent auto-upgrade). Does two things:

1. Writes `%APPDATA%\EVA\fresh-install` containing the installed version string. `main.js` reads and deletes this file on the next launch to determine whether to show the Welcome screen or the What's New modal. Both install modes ("Only for me" and "Anyone using this computer") write to the per-user folder: for a machine-wide install NSIS resolves `$APPDATA` to `C:\ProgramData`, so `custom.nsh` switches to the current user's shell context (`EVA_UserContext` / `EVA_RestoreContext`, keyed on electron-builder's `$installMode`) around every macro that touches user data. Before this fix (v0.0.9 and earlier) a machine-wide install put the marker in `C:\ProgramData\EVA`, so the Welcome / What's New screen never showed and the uninstaller targeted the wrong folder.
2. Deletes `%APPDATA%\EVA\Cache\` (Chromium disk cache). This forces a fresh fetch of all static assets on the next launch, preventing stale cached files (e.g. `CHANGELOG.md` from a previous version) from being served after an update. Chromium recreates the directory automatically.

**`customHeader`** — Overrides the branding text on all installer pages to `"EVA <version>"`.

**`customUnInit`** — Uninstaller `.onInit`. Shows a checkbox dialog asking whether to delete all EVA data: `%APPDATA%\EVA\` (conversations, settings, RAG vector database) and EVA's saved API keys and sign-in key in Windows Credential Manager.

```nsis
StrCpy $EVA_DelData "0"     ; default = KEEP data
IfSilent EVA_SkipDialog     ; silent upgrade: skip dialog, preserve data

StrCpy $EVA_DelData "1"     ; interactive default = delete (checkbox starts checked)
; ... nsDialogs checkbox ...
EVA_SkipDialog:
```

The `IfSilent` guard is critical. During an upgrade, the new installer calls the old uninstaller with `/S` (silent). Without this guard, the dialog appears mid-install — and the old default was delete, silently wiping user data on every upgrade.

**`customUnInstall`** — Deletes `%APPDATA%\EVA\` and every Windows Credential Manager entry named `eva` or ending in `@eva` (provider/MCP keys and the signing key, listed with `cmdkey /list`), only if the user confirmed deletion. Silent upgrades never reach it. The service name is the `EVA_CRED_SERVICE` define (default `eva`) so tests can use dummy entries.

## Auto-Update Flow

`electron-updater` (`^6.1.7`) is wired in `main.js`. The update lifecycle:

```
App launches → 3s delay → autoUpdater.checkForUpdates()
      ↓
latest.yml fetched from the repository's GitHub Releases (build.publish in package.json)
      ↓ (if newer version exists)
Silent background download
      ↓
Badge appears in renderer (update-status IPC: 'available' → 'downloading' → 'ready')
      ↓
User clicks badge → window.electronAPI.installUpdate()
      ↓
autoUpdater.quitAndInstall(true, true)   ← silent NSIS /S + force relaunch
      ↓ (NSIS customInstall macro runs during silent install)
%APPDATA%\EVA\fresh-install written with new version
      ↓
On next launch: fresh-install read + deleted → eva.db exists → app-updated IPC → What's New modal
```

**IPC surface (via `preload.js`):**

| Method | Direction | Payload |
|---|---|---|
| `onUpdateStatus(cb)` | main → renderer | `{ status: 'available' \| 'downloading' \| 'ready', percent?: number }` |
| `offUpdateStatus(cb)` | — | removes listener |
| `installUpdate()` | renderer → main | triggers silent install + relaunch |
| `onAppUpdated(cb)` | main → renderer | new version string (fires once after update) |
| `offAppUpdated(cb)` | — | removes listener |

**`publish` config in `package.json`** generates two files at build time:
- `installer/latest.yml` — published with the release; `electron-updater` fetches this to check for updates
- `resources/app-update.yml` (inside ASAR) — tells `electron-updater` where to look at runtime

**Silent upgrade and data safety:** `quitAndInstall(true, true)` runs the NSIS installer with `/S /FORCE_RUN`. The `IfSilent` guard in `custom.nsh` (`customUnInit`) detects this silent run and skips the "delete user data?" dialog, preserving `%APPDATA%\EVA\` unconditionally.

### `obfuscate-renderer.js` — JS Bundle Obfuscation

**Optional and off by default.** Default builds ship the readable, auditable renderer code. Pass `-Obfuscate` to `build-electron.ps1` (or `build-all.ps1`) to run it after `build-frontend.ps1`; it applies control-flow flattening, string array RC4 encoding, and hex identifier renaming to `frontend/dist/assets/*.js`. It only touches the React bundle, never `main.js` or the Python backend. A stamp tied to `dist/index.html` stops a default build from shipping a dist that an earlier `-Obfuscate` run obfuscated (rebuild the frontend instead), and stops `-Obfuscate` from obfuscating the same bundle twice.

## Build Scripts

All scripts in `build/scripts/`. Run from any directory — all paths resolve relative to `$PSScriptRoot`.

### `build-backend.ps1` — Python Backend (PyInstaller)

**Input:** `backend/` + `backend/eva.spec`
**Output:** `backend/backend-dist/eva-backend/`
**Runtime:** 10–20 minutes

| Step | Detail |
|---|---|
| 1/7 Locate uv and locks | Requires `uv` on PATH (`winget install astral-sh.uv`). Checks that `backend/requirements.lock` and `backend/requirements-build.lock` exist. There is no conda environment and no hard-coded path. |
| 2/7 Lock freshness | Re-resolves `requirements.txt` and `requirements-build.in` against a copy of the committed locks and fails if the result differs (someone changed the direct requirements without re-locking). Needs network; skip with `-SkipLockCheck`. |
| 3/7 Build environment | Creates a disposable Python 3.11 venv with `uv venv --python-preference only-managed` (uv's own CPython, never a system or conda Python) and installs both locks with `uv pip sync --require-hashes`. The environment lives in `backend/build-tmp/envs/py311-<hash>` and is cached by the hash of the two lock files; older environments are deleted. `build/scripts/check_build_env.py` then verifies every locked package, the key pins (`litellm==1.106.0`, `mcp>=2.2`, `pypdf==6.21.1`) and that PyMuPDF is absent. `-RebuildEnv` discards the cache. |
| 4/7 Stage models | Downloads the `all-MiniLM-L6-v2` ONNX model (86MB) pinned to a Hugging Face commit and checks `model.onnx` and `tokenizer.json` against SHA-256 values in the script; the download is skipped only if the cached files already match, and a mismatch fails the build. To change the model, update the revision and both hashes together. Generates `tiktoken_cache/` (cl100k_base + o200k_base) if not present. Both are gitignored and persist between runs. Runs with the build environment's Python. |
| 5/7 PyInstaller | `python -m PyInstaller eva.spec --clean -y` from the build environment. Deletes previous `backend-dist/` first. |
| 6/7 Copy tools and verify | Copies `tools/default/*.py` into `_internal/tools/default/` and writes `__init__.py` markers (PyInstaller does not bundle modules loaded via `importlib.import_module()`; `eva.spec` adds what those files import to `hiddenimports`). Replaces the bundled Visual C++ runtime (`msvcp140`, `vcruntime140`, `vcruntime140_1`) with the newest copy found in System32 or a Visual Studio redistributable folder, and fails if none is 14.40 or newer, because onnxruntime crashes against the 2019 runtime that uv's Python ships. Then fails the build if `fitz`/`pymupdf` is in the bundle or `pypdf` is missing (checked in PyInstaller's module list). |
| 7/7 Smoke test | Runs the packaged `eva-backend.exe` against a throw-away database on port 8000 (`backend/scripts/smoke_test_packaged_backend.py`, a test tool that is never packaged; it uses a temp database, vector store and workspace and never touches real data): health, signup/login, daemons, provider data, and the counts of tools, default agents, skills, default MCPs and the migration head, which are worked out from the source tree on every run (nothing is hard-coded, so adding a tool, agent or migration needs no change here), a PDF through ingest and search, a locked PDF, and a log scan for missing modules. Any failure fails the build. `-SkipSmokeTest` skips it; port 8000 must be free. |

**Changing dependencies:** edit `backend/requirements.txt` (runtime) or `backend/requirements-build.in` (PyInstaller), re-run the `uv pip compile` command in that file's header, and commit the regenerated `.lock`. The build refuses to run on a stale lock.

`$ErrorActionPreference = 'Continue'` throughout: PowerShell 5.1 wraps native stderr as `NativeCommandError` with `-Stop`. PyInstaller writes progress to stderr. Exit codes are checked explicitly after each critical command.

### `build-frontend.ps1` — React Frontend (Vite)

**Input:** `frontend/`
**Output:** `frontend/dist/`
**Runtime:** 1–2 minutes

Installs dependencies with `npm ci` (skipped when `package-lock.json` and `package.json` are unchanged since the last install), then runs `npm run build` (`tsc -b && vite build`). The type-check is part of the build and a type error fails it.

`frontend/.env.production` sets `VITE_API_BASE=/api`. The production bundle calls `/api/*` on the renderer's own origin (`http://127.0.0.1:5174`), and the Node.js proxy in `main.js` forwards those calls to the backend on port 8000, stripping the `/api` prefix, exactly as the Vite dev server does.

After the Vite build completes, the script copies `docs/CHANGELOG.md` → `frontend/dist/docs/CHANGELOG.md`. The static file server in `main.js` serves everything from `frontend_dist/`, so this is the only way to make the changelog reachable at `/docs/CHANGELOG.md` in the installed app. `WelcomePanel.tsx` fetches this URL to populate the "What's New" section.

### `build-electron.ps1` — Electron Packaging

**Input:** `frontend/dist/` + `backend/backend-dist/eva-backend/`
**Output:** `installer/EVA-Setup.exe`
**Runtime:** 5–10 minutes

| Step | Detail |
|---|---|
| Preflight | Checks both dist directories exist. Fails with a clear error if either is missing. |
| Kill processes | Force-kills `EVA`, `EVA.exe`, `eva-backend`, `electron`. Windows holds file handles on large executables inside `installer/`. |
| Clean output | Deletes `installer/` via `cmd /c rd /s /q`. Uses `cmd` not `Remove-Item` to avoid PowerShell file-handle quirks on large directories. |
| npm ci | Runs `npm ci` (exact versions from `package-lock.json`; fails if the lock and `package.json` disagree) whenever either file changed since the last successful install. Skipped otherwise. |
| Obfuscation | Off by default. `-Obfuscate` runs `obfuscate-renderer.js` on the renderer bundle (see above). |
| electron-builder | `npm run build:win` → `electron-builder --win` → reads `package.json`, copies `extraResources`, runs `after-pack.js`, compiles `custom.nsh`, produces `EVA-Setup.exe`. |

### `build-all.ps1` — Convenience Wrapper

```powershell
.\build-all.ps1               # Full build
.\build-all.ps1 -SkipFrontend # Backend changed only
.\build-all.ps1 -SkipBackend  # Frontend/Electron changed only
.\build-all.ps1 -Obfuscate    # Also obfuscate the renderer bundle (default: readable)
```

## Releases

Releases are produced by a tag-triggered GitHub Actions workflow on a GitHub-hosted Windows runner. Pushing a tag such as `v0.1.0` starts the pipeline.

| Step | What runs |
|---|---|
| 1. Checkout | `actions/checkout` with full history (needed to find the previous tag). |
| 2. Sync version from tag | Patches the `version` field of `build/package.json` from the git tag (e.g. `v0.1.0` → `"0.1.0"`). The patched file is not committed back. |
| 3. Build backend | `build-backend.ps1` (PyInstaller). The runner creates the Python environment, ONNX model and tiktoken cache itself, or restores them from the Actions cache. |
| 3b. Sync tool plugins | Copies `tools/default/*.py` into `_internal/tools/` even when the backend build is restored from cache, so tools are never stale. |
| 4. Build frontend | `build-frontend.ps1` (type-check, Vite build, CHANGELOG copy, ~2 min). |
| 5. Build installer | `build-electron.ps1` (electron-builder, ~5 min). |
| 6. Publish | `gh release create` uploads `EVA-Setup.exe`, its blockmap and `latest.yml` to this repository's GitHub Releases. |

Release notes are sourced from `docs/CHANGELOG.md`. Update it before tagging — it becomes both the GitHub release description and the in-app What's New content.

### Tagging a Release

```powershell
cd <repository-root>

# 1. Update docs/CHANGELOG.md with the new version entry
git add docs/CHANGELOG.md
git commit -m "chore(release): update changelog for v0.x.y"
git push origin main

# 2. Tag and push — triggers the release workflow
git tag v0.x.y
git push origin v0.x.y

# 3. Monitor the run on the repository's Actions tab, then check the Releases page
```
